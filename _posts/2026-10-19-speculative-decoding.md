## 一、先抛结论：推测解码是「免费的午餐」，但 2026 年它正在变复杂

自回归大模型有一个结构性的痛：**生成第 N 个 token，必须等前 N-1 个都算完**。每吐一个字，就要把整个几十上百亿参数的网络完整跑一遍（一次完整的前向），而这次前向主要卡在**显存带宽**上——权重和 KV Cache 从显存搬进计算单元的时间，远大于真正做乘加的时间。于是单条请求的解码几乎是「算力闲着、带宽拉满」的内存受限（memory-bound）状态。

推测解码（Speculative Decoding，也叫投机解码/推测采样）正是冲着这个浪费去的，核心思想一句话就能说清：

> **用一个便宜的「草稿」一口气猜出未来 K 个 token，再让大模型用一次并行前向同时验证这 K 个，接受其中正确的前缀，只在第一个出错处纠正。**

关键在于：大模型**验证 K 个 token 和生成 1 个 token，前向成本几乎一样**（同样是把权重搬一遍，只是序列维度多了 K，而这段计算是算力受限、带宽几乎不增加）。所以只要草稿「猜得准」，一次大模型前向就能产出好几个被确认的 token，吞吐自然成倍上涨。更妙的是——**这件事可以做到完全无损**：通过一个精心设计的接受/拒绝采样规则，最终输出的概率分布与原模型逐 token 解码**严格一致**。换句话说，它不是近似、不掉点，是「同样的结果、更快拿到」。

如果你只记一句话：**推测解码几乎是 LLM 推理里少有的「免费午餐」——不改模型、不掉精度，纯靠工程把延迟打下来。但到了 2026 年，随着 Agent 长上下文、服务多样化负载和新架构（扩散 LM）的到来，这顿午餐开始要「算总账」了。**

## 二、技术原理：为什么「先猜后验」能无损提速

### 2.1 朴素自回归为什么慢

设目标模型为大模型 \(M_q\)（给出分布 \(q\)）。标准解码是：采样 \(x_1 \sim q(\cdot\mid \text{prompt})\)，再 \(x_2 \sim q(\cdot\mid \text{prompt}, x_1)\)……每一步一次完整前向。对单条请求（batch=1），GPU 的算力利用率常常只有个位数百分比，瓶颈全在把权重从 HBM 读出来。**既然一次前向的带宽成本已经付了，不如让它一次多干点活。**

### 2.2 草稿-验证两步走

引入一个便宜的草稿模型 \(M_p\)（分布 \(p\)，可以是小几十倍的模型、也可以是大模型自己长出来的几个预测头）：

1. **Draft（草稿）**：用 \(M_p\) 自回归地快速生成 K 个候选 token \(\tilde{x}_1 \dots \tilde{x}_K\)。因为它小，这 K 步很便宜。
2. **Verify（验证）**：把 prompt + 这 K 个候选**一次性**喂给大模型 \(M_q\)，并行拿到每个位置上 \(M_q\) 的分布 \(q_1 \dots q_{K+1}\)（注意位置 K+1 是「免费」多算出来的）。
3. **Accept/Reject（接受或纠正）**：从左到右逐个检验。对候选 \(\tilde{x}_i\)，以概率 \(\min\!\big(1, \tfrac{q_i(\tilde{x}_i)}{p_i(\tilde{x}_i)}\big)\) 接受；一旦某个被拒绝，就从「修正分布」\(\text{norm}(\max(0, q_i - p_i))\) 重采样一个 token 顶上，后面的候选全部丢弃。

这个接受/拒绝规则（Leviathan et al. 2023、Chen et al. 2023 各自独立提出）保证了**最终 token 的边际分布恰好等于 \(q\)**——这就是「无损」的数学来源。每一轮大模型前向，期望能确认 \(1 + \text{(接受长度)}\) 个 token，接受长度越高、草稿越准，加速比越大。

### 2.3 一个直觉类比

把大模型想成一位惜字如金但权威的评审，草稿模型是个话多的实习生。实习生飞快写一段草稿，评审**扫一眼整段**（一次前向）就知道从哪个词开始不对、把那个词改掉，前面对的直接采纳。评审看一整段和看一个词花的时间差不多，于是「话多的实习生 + 一眼定稿的评审」就比评审逐字憋字快得多——前提是实习生别太离谱。

## 三、家族谱系：草稿从哪来，决定了这项技术的分叉

推测解码这几年的演化，本质是围绕「**草稿 token 从哪里来、代价多大、准不准**」在做文章。我把主流路线梳理成三大家族：

- **① 独立草稿模型（independent drafter）**：用同系列的小模型当草稿（如 7B 配 70B）。实现直接，但要额外部署、额外占显存和一份独立 KV Cache，且小模型和大模型「口味」未必一致。这是最早的经典形态（Leviathan / Chen 2023）。
- **② 自推测 / 多头草稿（self-speculative）**：让大模型自己兼任草稿，省掉第二个模型。代表作 **Medusa**（在最后一层接几个并行预测头，一次猜多个未来位置）与 **EAGLE / EAGLE-2 / EAGLE-3**（在**特征层**而非 token 层外推，用一个轻量自回归头预测下一步隐状态，再配合**树状**候选，是目前开源栈里综合最强的方案之一）。优点是共享主干、部署简单；缺点是要训练这些头。
- **③ 检索 / n-gram 查表（retrieval / lookup）**：根本不用神经网络草稿，直接从 prompt 或历史文本里按 n-gram 匹配、「抄」出候选（prompt lookup decoding）。零训练、零额外参数，对代码补全、RAG、长文摘要这类「输出大量复述输入」的场景出奇地有效。

工程上，vLLM、TensorRT-LLM、SGLang 等主流推理引擎都已内置这些方案（尤其 EAGLE 系与 n-gram），让推测解码从论文走进了生产。**我的看法**：这三家不是互相取代，而是按场景选型——通用对话优先 EAGLE 类，复述型任务用 lookup，异构/多模型服务才上独立草稿。

## 四、2026 年 10 月的前沿：这顿「免费午餐」开始要算总账

读完这一周 arXiv 上的新工作，我的直观感受是：**推测解码正在从「怎么提高接受率」进入「在真实复杂负载下，提速到底是不是真的」的成熟期。** 下面五篇各自戳中一个要害。

### 4.1 《Acceptance Is Not Speed》：别再只盯「人均接受长度」（arXiv:2610.23818）

这篇是我这周读到最有「打假」意味的一篇。长期以来大家用「每轮验证接受的 token 数（acceptance length）」衡量提速。作者指出：**无损验证下这个指标确实靠谱，但一旦用「放松的有损验证」（relaxed/lossy verification，为了更高接受率而接受本该拒绝的 token），它就会骗你。** 他们在 12 组目标-草稿配对上实测：最激进的有损设置平均每轮接受的 token 多了 **1.34 倍**，但生成的完成序列却**长了 1.54 倍**——多出来的 token 大多是低概率的、把推理链越拉越长的废话，表面提速被「输出变长」几乎抵消；而那些减少验证轮数的规则，准确率往往明显下滑，有些失败正是「推理没完没了、把答案预算耗光」。结论掷地有声：**只报「人均接受长度」不可信，必须同时报完成长度和验证轮数。**

**我的看法**：这是对整个领域评测文化的一次必要纠偏。推理模型（长 CoT）时代，有损加速与「让模型多想」之间界限模糊，很容易把「变啰嗦」误读成「变快」。做工程选型时，唯一诚实的指标是**端到端 wall-clock 延迟 + 任务准确率**，别被接受率的漂亮数字带偏。

### 4.2 DLite：为 Agent 的长上下文做「无历史草稿」（arXiv:2610.23787）

这篇直指 Agent 时代的新痛点。Agentic 工作负载是**超长且不断增长的上下文 + 频繁多轮交互**。作者观测到：在这种负载下，现有草稿模型的接受长度**最多退化 80%**，而为草稿单独维护一份随上下文膨胀的历史 KV Cache，系统开销巨大。DLite 的思路很干脆——**不要历史**：直接复用目标模型已经算出的上下文隐状态，做「局部的简单预测」，再用一个轻量顺序头补回块内因果依赖，把「越来越难的全局建模」降维成「局部好做的预测」。配合专门的两阶段训练，在通用、长上下文和 Agent 负载上拿到 2～6 的接受长度，比 SOTA 方法 DSpark 最多再快 70%。

**我的看法**：这是我最看好的方向之一。随着应用主体从「一问一答」转向「长时运行的 Agent」，上下文爆炸会让传统草稿模型迅速失效。「无历史 / 复用目标隐状态」几乎是必然趋势——它和 EAGLE 在特征层做文章是同一哲学的延伸：**草稿越贴着目标模型的内部表示，越省、越准。**

### 4.3 BS-Spec：用「同一个模型的高位比特」当草稿（arXiv:2610.22877）

这篇把推测解码和低比特量化、硬件协同设计缝在了一起，思路很硬核。传统方案要么要独立草稿模型（多一份权重和 KV），要么自推测配置对负载不敏感。BS-Spec 基于**块浮点（BFP）**做「比特共享」：从同一个 BFP 目标模型里，**只加载权重和 KV 的高位比特（MSB）、保留共享指数**，就地派生出多个精度档的「草稿表示」，彻底省掉第二份模型存储；再离线校准，为不同服务场景（batch、上下文长度各异）挑选最优的权重/KV 精度组合，运行时查表切换，并配一个 LUT 驱动的混合精度加速器执行。结果：相比自回归最多 **1.9 倍**提速，相比同类比特共享自推测基线平均再快 **67.2%**。

**我的看法**：把「草稿 = 目标模型的低精度版本」这件事做到硬件层，是很优雅的资源复用——草稿和目标天然同源、几乎零额外内存。代价是强依赖 BFP 格式与定制数据通路，更像是给自研推理芯片/专用部署准备的方案，短期难在通用 GPU 上普及，但指明了「软硬协同压榨带宽」的方向。

### 4.4 SPOT：把推测解码迁移到扩散语言模型（arXiv:2610.22543）

扩散语言模型（我在 10 月 13 日那篇写过）主打并行生成，却卡在「速度-质量」权衡：精确解码每轮只敲定一个掩码位置，激进的多 token 并行解码又是有损的。而经典推测解码不能直接搬过来——因为扩散 LM 要同时决定**生成什么**和**在哪生成**。SPOT 的洞察是：**模型自己上一轮的预测，在 92～100% 的位置上已经给对了 token，缺的只是「下一个该敲定哪个位置」的顺序。** 于是它训练一个仅 **0.62M 参数**的小模型，只读目标模型的输出分布，提出一棵候选「提交顺序」树，目标模型一次前向验证整棵树（检查每个候选是否等于自己的下一状态），并用耦合噪声匹配支持任意温度下的树状推测。实测把目标前向次数最多砍到 **1/6.8**，吞吐达标准解码的 **3.2 倍**，且学到的草稿器能在 6 个不同扩散 LM 间迁移。

**我的看法**：这篇的价值在于证明「草稿-验证」的无损加速范式**不是自回归的专利**。扩散 LM 要想在工程上真正跑赢自回归，必须解决自己的推理加速栈，SPOT 把推测解码里「猜内容」的智慧巧妙改造成「猜顺序」，是漂亮的范式迁移。

### 4.5 稀疏协同解码：什么时候该「叫大模型来一下」（arXiv:2610.23613）

前四篇都在「密集验证」（每轮都请大模型验证）框架里。这篇反过来问：能不能让草稿模型**自己跑大部分 token，只在短的纠错片段才调用大模型**（稀疏协同）？难点全在「**何时触发**」。作者的关键发现很反直觉：**局部不确定性是个糟糕的触发信号**——熵、负对数似然、logit 边距、top-k 质量等特征预测「草稿会不会错」的 AUC 只有 0.50～0.53（近乎瞎猜）；而**草稿置信度轨迹的整体形状特征**用一个轻量逻辑回归就能到 AUC 0.86。在线使用时，比最好的开环（固定）调度在 GSM8K 上提升 5.3～20 个准确率点。

**我的看法**：「看单步犹豫没用、看整条轨迹的走势才有用」这个结论很有启发——它和强化学习里「稀疏奖励要看轨迹」是相通的。稀疏协同把推测解码从「大模型主导、草稿打下手」反转为「草稿主导、大模型兜底」，更省；但它**不再严格无损**，收益高度依赖「触发预测准 + 草稿本身够强」，论文里也坦承在某些任务上会掉点，属于「用正确性换速度」的可调旋钮。

## 五、应用场景：哪里最该上推测解码

- **低延迟对话/助手（batch 小、追求首字后流畅度）**：最经典受益场景，单请求 memory-bound，EAGLE 类即插即用。
- **代码补全 / IDE**：输出大量复述上文符号，n-gram lookup 草稿命中率极高，近乎零成本。
- **RAG / 长文摘要**：答案常大段引用检索到的原文，检索型草稿事半功倍。
- **长时运行的 Agent（多轮、长上下文、工具调用）**：2026 年的新主场，但传统草稿会退化，需 DLite 这类无历史方案。
- **推理模型（长 CoT）**：收益可观，但务必警惕 4.1 的「长度膨胀」陷阱，坚持用端到端延迟而非接受率评估。
- **边缘/专用硬件部署**：BS-Spec 式「草稿=低精度自身」配合定制数据通路，适合自研芯片。

**要清醒的一点**：推测解码主要优化**单请求/小 batch 的延迟**。当服务端把 batch 堆得很大、GPU 已经算力受限（compute-bound）时，额外的验证计算反而可能拖慢整体吞吐——此时它的收益会显著缩水甚至转负。这也是为什么「负载感知」（像 BS-Spec 那样按 batch/上下文选配置）会成为 2026 年的关键词。

## 六、优缺点与同类方案对比

### 6.1 优点

- **无损**（经典版本）：输出分布与原模型严格一致，不掉点，这是它相对其他加速法最大的护城河。
- **即插即用**：不改目标模型权重（独立草稿 / lookup 甚至零训练），对已上线模型友好。
- **与其他优化正交**：可叠加量化、PagedAttention、连续批处理等，收益基本独立相加。

### 6.2 缺点 / 局限

- **大 batch 下收益衰减**：高并发、算力受限时验证开销可能得不偿失。
- **依赖「草稿准」**：领域漂移、长上下文、Agent 多轮会让接受率骤降（DLite 要解决的正是这个）。
- **额外成本**：独立草稿要多一份显存和 KV；自推测头要训练；有损变体会牺牲无损性甚至准确率。
- **评测易被误导**：接受长度 ≠ 真实提速（见 4.1）。

### 6.3 与同类 LLM 推理加速方案对比（我的归纳）

| 维度 | 推测解码 | 权重量化（INT8/4/低比特） | KV Cache 压缩/驱逐 | 蒸馏成小模型 |
|---|---|---|---|---|
| 是否改输出质量 | **无损**（经典版） | 轻微掉点（取决比特） | 可能掉点（丢上下文） | 明显改变（是另一个模型） |
| 是否改模型权重 | 否（目标不变） | 是（量化权重） | 否 | 是（重训） |
| 主要收益来源 | 每次前向多出 token | 降带宽/显存占用 | 降 KV 显存与带宽 | 直接缩小模型 |
| 对大 batch | 收益衰减 | 收益保持 | 收益保持 | 收益保持 |
| 能否叠加 | **能叠加其余三者** | 能 | 能 | — |
| 典型代表 | EAGLE-3 / Medusa / lookup | GPTQ / AWQ / BitNet | H2O / SnapKV | MiniLM 等 |

一句话：**推测解码和量化/KV 压缩不是竞品，而是互补**——前者省「步数」，后者省「每步的带宽/显存」，叠起来用才是生产最优解。

## 七、给读者的落地建议（可执行清单）

1. **先量化瓶颈再决定上不上**：用 nvidia-smi / 引擎自带 profiler 看你的服务是 memory-bound（小 batch、低利用率）还是 compute-bound（大 batch）。只有前者，推测解码才划算。
2. **优先用引擎内置的 EAGLE / n-gram**：vLLM、TensorRT-LLM、SGLang 都已支持，别自己从零造；复述型任务（代码、RAG）先试零成本的 prompt-lookup。
3. **只信端到端指标**：benchmark 必须报 **wall-clock 延迟 + 任务准确率 + 完成长度**，别被「接受率/接受长度」单指标忽悠（4.1 的教训）。
4. **做负载分档**：为不同 batch/上下文长度准备不同草稿配置或开关，高并发时段考虑自动关掉推测解码。
5. **Agent 场景单独评测**：长上下文会让传统草稿退化，关注 DLite 这类无历史方案，并在你真实的多轮轨迹上测，而非短 prompt。
6. **叠加而非二选一**：把推测解码和量化、KV 压缩、连续批处理组合，收益通常可叠加。
7. **谨慎对待有损变体**：relaxed verification 能再快一点，但要盯死准确率和输出长度，确认没有「越想越长、越长越慢」。

## 八、结语：从「怎么更快」到「在真实世界里是不是真的更快」

推测解码诞生时是个近乎完美的工程 trick：不掉精度、不改模型、白送 2～3 倍。2026 年这一周的论文让我看到它在**成熟**——研究者不再满足于更高的接受率，而是开始追问：在 Agent 的长上下文里它还成立吗（DLite）？在推理模型的长 CoT 里「接受多」是不是「变慢了」（Acceptance Is Not Speed）？能不能干脆用模型自身的低比特当草稿（BS-Spec）、迁移到扩散 LM（SPOT）、甚至反客为主让草稿主导（稀疏协同）？

**我的总判断**：推测解码不会有「大一统」的单一最优解，而会沿着「草稿越贴近目标内部表示（EAGLE→DLite）」「草稿与目标共享参数/比特（BS-Spec）」「按负载动态配置」三条线继续分化，并越来越深地嵌进推理引擎与硬件。对使用者而言，真正的能力不是知道它能提速，而是**知道在你的负载下它到底提没提速、有没有悄悄牺牲质量**——而这，恰恰是这周这批论文集体想教给我们的事。
