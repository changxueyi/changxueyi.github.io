## 一、先抛结论：CUA 的难点不在「点一下」，在「连着点一百下还不翻车」

Computer-Use Agent（下称 CUA，也常叫 GUI Agent）要做的事一句话能说清：**让模型像人一样看屏幕、动鼠标键盘，直接在真实的操作系统、浏览器或手机 App 里替你把活干完**——订机票、填表单、整理表格、在后台系统里走一套审批流程。

这件事最反直觉的地方在于：**单步「点对一个按钮」早就不是主要矛盾了**。真正难的是把几十上百个原子动作串成一条**既能完成任务、又稳定、又可回滚、还不会在中途干出不可逆坏事**的轨迹。2026 年 10 月这批论文的集体转向，恰恰印证了这一点：大家不再只比「任务最终成功率」，而是开始系统性地研究**执行稳定性、可验证奖励、以及如何监管一个会自己动手的 Agent**。

如果你只记一句话：**CUA 的 2026 年主线，是从「能力 demo」走向「可靠性工程」。**

## 二、背景与动机：为什么非得让模型「直接用电脑」

过去做自动化有两条成熟路线，但都有硬伤：

- **API / RPA（机器人流程自动化）**：靠接口或录制好的脚本操作。稳定、快、可审计，但**脆**——界面一改、字段一变、弹个验证码，脚本就断；而且世界上绝大多数软件、内部系统、老旧后台**根本没有对外 API**。
- **纯文本 Web Agent**：把网页 DOM 转成文本喂给大模型（WebArena 这类基准即此范式）。能处理结构化网页，但面对 Canvas 绘制的界面、桌面软件、图片化按钮就无能为力，也不符合「人怎么用就怎么用」的通用目标。

CUA 的野心是**用一个通用策略覆盖所有带图形界面的软件**：不依赖 API，不依赖人工写脚本，模型自己看像素、自己决定下一步。2024–2025 年，Anthropic 的 Claude computer use、OpenAI 的 Operator（CUA 模型）、Google 的 Project Mariner 把它推成了产品级方向；学术侧 OSWorld、WebArena、AndroidWorld 等基准提供了统一的「真实环境 + 任务 + 验证」评测场。到 2026 年，方向确立之后，**瓶颈从「可行性」变成了「可靠性与规模化训练」**——这正是本文要展开的。

## 三、技术原理：一个跑在真实系统上的闭环

把 CUA 拆开看，核心是一个**感知 → 推理 → 执行 → 环境反馈**的闭环（见题图左半部分）。

### 3.1 感知（Observation）
Agent 的「眼睛」通常是三样东西的组合：

1. **屏幕截图**——最通用，什么界面都能看，但模型得自己从像素里认出「哪里是可点的按钮」；
2. **无障碍树（accessibility tree）/ DOM**——结构化的 UI 元素列表，带坐标和语义，但不是所有应用都暴露、且常常又长又噪；
3. **Set-of-Marks（标记集）**——给截图里的可交互元素打上编号框，让模型用「点 7 号」而不是「点坐标 (834,210)」来表达动作。这是把「视觉定位」转成「选择题」的关键工程技巧，大幅降低了点击坐标回归的难度。

**GUI grounding（界面定位）**——即把「我想点那个保存按钮」精确映射到屏幕上的像素/元素——是整条链路的地基。2026 年 10 月的 GroundGUI（arXiv:2610.19100）就专门用「高质量数据 + 蒸馏到强化学习」来提升 grounding；OS-Helix（arXiv:2610.22234）则主张**把 GUI 交互与代码执行统一起来**，让 Agent 在「点界面」和「直接写/跑代码」之间自由切换——这其实承认了一个现实：**纯点界面并不总是最优解，能用命令行/脚本解决的就不该硬点**。

### 3.2 推理（Policy / VLM）
「大脑」是一个视觉语言模型（VLM）。它读入观测，产出下一步动作，通常还夹带**规划、反思、记忆**：先想清楚整体步骤，执行后检查屏幕是否如预期变化，没达预期就纠偏。记忆尤其关键——跨步骤要记住「我已经填过收件人了」。GUI Agent 的记忆该用哪种模态（截图？文本摘要？元素列表？）本身就是研究问题，*Learning How to Remember*（arXiv:2610.17928）即在讨论「记忆模态选择」。

### 3.3 执行（Action）
动作空间是一组原子操作：`click / double-click / type / scroll / key / drag`，越来越多实现还加上 `exec code`（执行一段代码）。注意**这是对真实系统的真实写操作**：它会真的发邮件、真的改数据库、真的下订单。

### 3.4 环境反馈与奖励（Verifier / Reward）
训练 CUA 最大的工程障碍是**奖励从哪来**。数学、代码有现成的「对/错」判定，GUI 任务却很难自动判对错。2026 年的主流解法是**execution-validated verifier（执行校验式验证器）**：任务跑完后，去真实环境里检查状态是否满足目标（文件是否生成、表格某格的值是否正确、邮件是否出现在发件箱），用这个可验证信号做强化学习（RLVR，可验证奖励的强化学习）的 reward。MAI-Gym（arXiv:2610.20939）明确提到它合成「带执行校验式任务验证器」的可重置模拟 App，正是奔着这个去的。

## 四、2026 年研究到底在造什么（题图右半部分）

我把这一周扎堆出现的工作归成六层，正好拼出一张「CUA 要落地还缺什么」的地图：

| 层次 | 代表工作（2026-10） | 在解决的问题 | 我的解读 |
|---|---|---|---|
| 界面定位 Grounding | OS-Helix(2610.22234)、GroundGUI(2610.19100) | 像素→可交互元素的精确映射；界面与代码统一 | 地基；grounding 不稳，上层全白搭 |
| 环境与 RL 训练 | MAI-Gym(2610.20939)、SoftwareGym(2610.12611) | 交互环境太贵、真实任务太少 → 合成 App、万级并行、在线 RL | 2026 的真正主战场：规模化造训练场 |
| 开放全栈 | OpenGCUA(2610.22200) | 数据+策略+评测一起开源 | 把「闭源能力」变成社区可复现基座 |
| 技能与记忆 | Work2Skill(2610.12984)、Learning How to Remember(2610.17928) | 把人类 GUI 操作经验沉淀成可复用技能 | 让 Agent 不必每次从零摸索 |
| 可靠性诊断 | GraceBench(2610.19900) | 不止看最终成功，还看轨迹是否稳定 | 我认为这是今年最重要的范式转变 |
| 安全与监管 | LEASH(2610.22280)、Safe Autonomy(2610.18508) | 不确定时升级人类/强模型接管 | 决定 CUA 能否进真实生产环境 |

**我想重点展开两个我认为被低估的点。**

**其一，GraceBench 代表的「轨迹稳定性」转向。** 它的摘要讲得很直白：在自动化工作流里，哪怕 Agent 最终完成了任务，**中途的多余动作、绕路、错误操作也会污染采集的数据、引入不可逆的副作用、动摇信任**。所以它系统性地诊断执行稳定性——Agent 是否偏离可行路径、是否陷入死循环、是否停滞、能否从不稳定动作里恢复。**我的看法**：这是 CUA 走向生产的分水岭。一个「80% 成功率但偶尔会误删文件」的 Agent，和一个「80% 成功率且失败时安全停下」的 Agent，是两种完全不同的产品——后者才敢交给企业用。只盯最终成功率，等于只看考试分数不看他有没有在考场里打翻别人的桌子。

**其二，MAI-Gym / SoftwareGym 代表的「训练场规模化」。** MAI-Gym 的摘要点明了核心矛盾：带可验证奖励的在线 RL 在数学、代码、工具调用上已经跑通，但**搬到 GUI Agent 上非常难，因为交互环境成本高、真实训练任务稀缺**。它的解法是统一移动/桌面/网页的 rollout 管线、支持两万个并行环境、还能自动合成可重置的模拟 App 与跨 App 任务。**我的看法**：这其实是在复刻「代码/数学能力起飞」的那套配方——**可验证奖励 + 海量可并行的环境**。谁能把 GUI 世界的训练场造得又多又真又可验证，谁就能复制那条增长曲线。CUA 下一波能力跃迁，很可能不来自更大的模型，而来自更好的 gym。

## 五、应用场景

- **跨系统办公自动化**：在没有 API 的内部 ERP/CRM/审批系统里跑流程，这是 RPA 最想要却最脆的场景，CUA 的通用性正好补位。
- **QA 与软件测试**：让 Agent 像真人一样点遍 App 做回归测试；GraceBench 式的稳定性诊断天然契合。
- **数据录入与迁移**：把一个系统里的数据搬到另一个系统，中间要跨多个界面。
- **个人助理 / 消费级**：订票、比价、填表、处理琐碎的网页事务（Operator、Mariner 的目标场景）。
- **无障碍辅助**：替行动不便或不熟悉软件的用户操作复杂界面。

**我的看法**：短期内最先跑通的，一定是**高价值 + 可容忍人工复核 + 失败代价可控**的场景（比如内部运营的半自动流程，人在回路里点「确认」）。「完全无人值守地替你管钱、发不可撤销的指令」还远不到时候——这正是 LEASH 那类「不确定就升级给人」的工作要托底的地方。

## 六、优缺点

**优点**
- **通用**：理论上覆盖一切有图形界面的软件，不挑有没有 API；
- **贴近人类工作流**：不用为每个系统写专用集成，模型「照着人怎么用」学；
- **可借力基础模型**：VLM 越强，grounding 和规划越好，吃到大模型进步的红利。

**缺点 / 现实约束**
- **慢且贵**：每一步都要截图 + VLM 推理，长任务延迟和成本都高（STP-GUI 2610.20390 这类「token 剪枝」工作就在抠效率）；
- **脆而难验证**：界面微变就可能失手，且 GUI 任务的自动奖励本就难造；
- **错误会累积且不可逆**：越长的任务越容易中途跑偏，而写操作一旦执行很难撤销；
- **安全面大**：会读你的屏幕、碰你的账号，还可能中招「界面上的提示词注入」（页面里藏一句话诱导 Agent 乱点）。**我的看法**：这是 CUA 独有且被严重低估的攻击面——它的「眼睛」直接吃屏幕内容，而屏幕内容是不可信输入。

## 七、与同类方案对比

| 维度 | 传统 RPA / 脚本 | 纯文本 Web Agent | Computer-Use Agent（视觉） |
|---|---|---|---|
| 覆盖面 | 窄（需逐个适配） | 中（只限网页 DOM） | 广（任意 GUI） |
| 对界面变化的鲁棒性 | 差（易断） | 中 | 较好（看语义而非写死坐标） |
| 速度与成本 | 快、便宜 | 中 | 慢、贵 |
| 可审计 / 稳定 | 强 | 中 | 当前较弱（正是研究热点） |
| 适用软件 | 有限 | 仅网页 | 桌面/网页/移动通吃 |

**我的判断**：未来一两年不会是「CUA 取代 RPA」，而是**分层混合**——能用 API/脚本精确、便宜、可审计地做的，就别让 CUA 去点；只有在没有接口、界面多变、需要「像人一样临场判断」的地方，才上 CUA。OS-Helix 把「点界面」和「跑代码」统一起来，本质上就是在系统层面承认这种混合是最优解。

## 八、给读者的可落地收获

如果你准备动手，我的七条建议：

1. **先问「有没有 API」**。有 API、流程稳定，老老实实用 API/RPA，别为了用 CUA 而用 CUA——它慢、贵、还更容易出错。
2. **从「人在回路」起步**。让 Agent 提议动作、人点确认，先把高价值低风险的半自动流程跑顺，再谈无人值守。
3. **优先用 Set-of-Marks + 无障碍树**，别一上来就逼模型回归像素坐标；能拿到结构化元素就尽量拿。
4. **把评测做成「稳定性 + 成功率」双指标**。借鉴 GraceBench 思路，记录绕路、死循环、停滞、误操作，别只看最终对没对。
5. **给动作加护栏**。危险/不可逆动作（删除、支付、发送）走白名单或二次确认；默认在沙箱/测试账号里跑。
6. **防「界面提示词注入」**。把屏幕上读到的文字当不可信输入，别让页面里的一句话左右 Agent 的决策。
7. **想自己训练，就先建 gym**。可验证奖励 + 可重置的环境是前提；没有能自动判对错的任务，RL 无从谈起——MAI-Gym/SoftwareGym 的思路值得抄。

## 九、结语：从「会用电脑」到「可靠地用电脑」

2025 年我们惊叹于「模型居然真的会自己点鼠标了」；2026 年 10 月这批论文告诉我们，**惊叹期结束了，工程期开始了**。OpenGCUA 在把能力开源成基座，MAI-Gym/SoftwareGym 在规模化造训练场，GraceBench 在重新定义「什么叫做得好」，LEASH 和 Safe Autonomy 在给它套上安全带。

**我最终的判断**：CUA 的下一个拐点，不会由「又大又强的模型」单独带来，而会由**可验证的训练环境 + 稳定性与安全的工程基建**共同决定。能力早已够炫，缺的是让人敢把真实权限交出去的那份可靠。谁先补齐这块，谁就先拿到「会用电脑的 AI」真正进入生产系统的入场券。
