> 本文基于社区流传的 Claude Code CLI 源码级分析资料整理，并加入我个人的理解与判断。具体实现以 Anthropic 官方最新版本为准；文中代码均为**说明性伪代码**，用于解释原理，不代表真实源码。

终端里的 AI 编码助手这两年很火，Claude Code 是其中做得相当扎实的一个。它不是"在命令行里套了个聊天框"那么简单——底层是一套**事件驱动的分层 Agent 引擎**。这篇我们从外到内，把它的技术原理拆开看一遍。

## 一、它到底是什么

Claude Code 是 Anthropic 出的**终端智能编码助手**：你在命令行里用自然语言提需求，它调用 Claude 模型，自动读写文件、跑 Git、执行 Shell 命令来完成任务。核心定位有四点：

- 终端里的 IDE 级编码体验（不用图形界面）
- AI 驱动的工作流自动化（文件、Git、Shell 全打通）
- 高度模块化的工具系统（约 41 个工具、50+ 斜杠命令）
- 多端集成（本地 CLI、IDE 插件、远程会话）

它要解决的痛点也很清晰：重复编码、频繁切文件、权限混乱、上下文丢失、成本不可控。

## 二、技术栈一览

| 层级 | 选型 | 说明 |
| --- | --- | --- |
| 运行时 | **Bun** | 启动快、打包、特性开关（`bun:bundle` 死代码消除） |
| 语言 | **TypeScript** | Strict 模式，基本无 `any` |
| CLI 框架 | **Commander.js** | 参数解析（`@commander-js/extra-typings`） |
| 终端 UI | **React + Ink** | 用 React 组件渲染终端界面（100+ 组件） |
| 数据校验 | **Zod (v4)** | 工具入参、配置校验 |
| 集成 | **@anthropic-ai/sdk**、**MCP SDK** | 主模型通信 + 第三方工具协议 |
| 可观测 | **OpenTelemetry / gRPC** | 懒加载，性能与追踪 |

一个值得注意的细节：OpenTelemetry、gRPC 这类"大而不常用"的依赖是**懒加载**的，Bun 的死代码消除 + 特性开关让冷启动尽量轻。这是 CLI 工具很在意的体验点。

## 三、整体架构：事件驱动的分层 CLI 引擎

```
┌───────────────────────────────────────────────┐
│  表现层  UI/REPL (Ink + React 组件)            │  渲染界面、捕获输入
├───────────────────────────────────────────────┤
│  协调层  QueryEngine + queryLoop               │  消息流转、API 调用、工具编排
├───────────────────────────────────────────────┤
│  工具层  41 个工具 + StreamingToolExecutor     │  文件/网络/代理/规划/调度
├───────────────────────────────────────────────┤
│  AI 引擎层  Anthropic SDK 封装                  │  流式响应、参数、错误恢复
├───────────────────────────────────────────────┤
│  支撑层  权限 / 消息 / 历史 / 成本 / MCP·OAuth·LSP │
└───────────────────────────────────────────────┘
```

这套分层的关键在于：**UI 与"大脑"解耦**。表现层只负责渲染和收集输入，真正的编排逻辑集中在协调层（QueryEngine），这让它能同时支持交互式 REPL、无头（headless）脚本、SDK 回调等多种运行模式。

## 四、大白话版：把它想成"编程秘书"

一次对话，秘书做的事其实是一个闭环：

1. 你说："改一下 `src/main.tsx` 第 100 行"
2. 秘书记成一条**用户消息**
3. 把需求 + 文件内容 + 历史 + 系统提示发给 Claude
4. Claude 回复方案："我要读这个文件、改这段、保存"
5. 秘书**执行工具**（读文件、改、存），每步都可能先问你"能做吗？"
6. 把执行结果回传给 Claude
7. Claude 基于结果继续想 / 收尾
8. 秘书向你汇报最终结果

四个关键词：**循环**（可多轮，记住上文）、**权限**（执行前问）、**并发**（多个工具同时干）、**记账**（消息历史 + 成本追踪）。

## 五、核心机制深入

### 1. 会话状态：QueryEngine

整个会话的"记忆"集中在一个可变对象里：

```ts
class QueryEngine {
  mutableMessages: Message[]               // 会话消息（持续增长）
  abortController: AbortController         // 中止信号
  permissionDenials: SDKPermissionDenial[] // 权限拒绝追踪
  readFileState: FileStateCache            // 文件缓存
}
```

消息本身是一个联合类型：用户消息 / Claude 回复（可能含 `tool_use`）/ 系统消息 / 工具进度。每条都带 `uuid`、`timestamp`、`permission_mode` 等元数据——这为压缩、回放、成本核算打下基础。

### 2. 灵魂：查询循环 queryLoop

Agent 的"心跳"就是这个**异步生成器**驱动的无限循环，直到满足停止条件：

```ts
async function* queryLoop(state) {
  while (true) {
    // 阶段1 准备：记忆预取、检查中止、按需压缩消息
    // 阶段2 API 调用：规整消息 → 选模型 → 构造请求(含41个工具定义) → 流式调用
    // 阶段3 响应处理：检测 tool_use → 权限检查 → 并发执行工具 → 收集结果回填 messages[]
    // 阶段4 继续决策：看 stop_reason
    //   end_turn → 结束
    //   tool_use → 带着工具结果继续
    //   max_tokens → 有限次恢复重试
    if (shouldStop) break;
  }
}
```

我认为这里最值得学的是两点：

- **用异步生成器（async generator）承载"边想边说边干"**：流式 token、工具进度、中间消息都通过 `yield` 往外吐，UI 层订阅即可，天然支持流式渲染和随时中止。
- **"是否继续"被显式建模成一组条件**（token 恢复重试、压缩触发、停止钩子、工具结果继续等），而不是一句拍脑袋的 `if`。Agent 的健壮性，很大程度就藏在这套"继续/停止"的判定里。

### 3. 工具系统：41 个工具 + 并发执行

工具是 Agent 的"手"。Claude Code 的工具走**注册 → 发现 → 权限检查 → 并发执行 → 结果收集**的流水线，由 `StreamingToolExecutor` 负责并发与安全检查。每个工具用 Zod 定义入参 schema，模型据此生成结构化调用。

设计上用了**模板方法**（Tool 基类定义统一执行流）+ **工厂**（工具注册）——加新工具只要实现基类约定，就能自动接入权限与并发框架。这套"可插拔工具"的抽象，是所有严肃 Agent 框架的共同点。

### 4. 权限决策树：Agent 安全的核心

这是我最欣赏的部分。每次工具调用前，`canUseTool` 会走一棵**分层决策树**，从"最确定"到"最需要人判断"逐级下降：

```
canUseTool(tool, input, ctx)
  ├─ 有强制决策？          → 直接返回
  ├─ 命中权限规则？        → allow / deny（alwaysAllow / alwaysDeny…）
  ├─ 分类器（如 Bash）？   → 有预测/投机分类：allow / deny / 不确定则继续
  ├─ 权限模式 PermissionMode：
  │    bypassPermissions → allow
  │    acceptEdits       → 编辑类 allow
  │    dontAsk           → deny
  │    auto / 其他       → ask
  └─ ask 分发：协调器 / Swarm worker / 交互式弹窗 / 无头自动拒绝 / SDK 回调
```

它把"要不要放行这次操作"拆成了**规则 → 分类器 → 模式 → 人机交互**四道闸，并且**所有拒绝都会被记录**用于事后报告。这解决了 Agent 落地最现实的矛盾：既要自动化，又不能让它在你机器上乱跑 `rm -rf`。

### 5. 上下文与成本：压缩 + 记账

长对话会撑爆上下文窗口，Claude Code 用两种压缩：**snip（本地摘要）** 和 **microcompact（API 端压缩）**，触发条件是消息数超阈值或 token 超预算，并用一条 `SystemCompactBoundaryMessage` 标记压缩边界。配套的 `cost-tracker` 全程追踪 token 用量与预算——**上下文管理和成本控制被当成一等公民**，而不是事后补丁。

## 六、设计模式赏析

- **Generator / Async-Generator**：流式响应、长任务
- **观察者**：权限钩子
- **工厂**：工具注册、命令创建
- **策略**：权限决策、压缩算法可替换
- **装饰器**：给工具包一层权限
- **中介者**：QueryEngine 居中协调消息 / 工具 / 权限
- **模板方法**：Tool 基类统一执行流

这套模式组合不是为了炫技，而是"把易变的部分（工具、权限策略、压缩算法）做成可插拔"，让核心循环保持稳定。

## 七、我的分析与启示

读完它的架构，我提炼出做 AI Agent 的一个通用范式，可以概括成一个公式：

> **Agent ≈ 循环(Loop) + 工具(Tools) + 权限(Permission) + 上下文管理(Context)**

几点具体启发：

1. **把"主循环"做成显式状态机 + 生成器**。别把 while 循环写成一坨；把"继续/停止"的条件、每个阶段的产出都显式化，Agent 的可控性和可调试性会好一个量级。
2. **工具要可插拔、入参要 schema 化**。用 Zod / JSON Schema 定义工具入参，模型生成结构化调用，既减少解析错误，也让加工具的成本趋近于零。
3. **权限是 Agent 的生命线，要分层**。规则能定的别问人，模型能判的交分类器，剩下的才弹窗问用户，并且要把拒绝记录下来——这决定了用户敢不敢把机器交给它。
4. **上下文与成本从第一天就要管**。压缩策略、token 预算、用量追踪不是优化项，是"能不能长时间跑下去"的前提。
5. **UI 与大脑解耦**。表现层只订阅事件流，核心逻辑与渲染分离，才能同时支持交互式、无头、SDK 三种形态。

顺带一提：我平时也在用 Codex 这类同类工具，思路是相通的——**终端 + 主循环 + 工具 + 权限**几乎是这一代编码 Agent 的"标准架构"。理解了 Claude Code 的这套拆解，再看别的 Agent 框架会轻松很多。

## 八、结语

Claude Code 给我的最大启发是：**做 Agent 的难点不在"接个大模型"，而在循环、工具、权限、上下文这四件"工程活"上**。模型只是发动机，能不能安全、可控、可持续地把活干完，靠的是外面这套引擎。
