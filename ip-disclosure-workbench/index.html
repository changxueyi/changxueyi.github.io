从材料到技术主张

不是把代码改写成文案，而是找出技术手段如何带来效果。

设计说明讲意图，代码与测试讲实际行为。将它们放到同一条证据链里，才能看清核心机制、替代方案和仍待确认的部分。

01 / SCOPE

限定分析范围

只读取指定项目与相关文件，跳过依赖、构建产物和疑似机密。

02 / TRACE

追踪技术机制

沿输入、处理、决策、状态变化、输出和异常路径整理实现。

03 / MAP

映射设计与证据

将方案特征关联到文档章节、代码符号、行号与测试结果。

04 / DRAFT

形成评审材料

输出候选专利点、交底初稿、实施方式和发明人问题清单。

有据可查 · 不做法律承诺

让每个候选点，都能回答三个问题。

问题是否具体？技术方案如何执行？效果由哪些证据支撑？

QUESTION / 技术问题

在哪种技术条件下失效？

描述输入、设备、网络、数据或处理约束，区别于产品愿望和纯业务目标。

MECHANISM / 技术手段

系统具体做了什么？

列出必要特征、执行顺序、组件关系和可替代的实施方式。

EFFECT / 技术效果

效果如何被验证？

区分测量结果与预期效果；证据不足时列出待补材料，不填造数据。

常见问题

为材料边界留出清楚的答案。

演示结果会被上传或保存吗？

不会。页面不调用网络接口，也不使用本地存储；输入仅保留在当前浏览器页面内。刷新后会恢复内置示例。

这个在线演示等同于完整专利分析吗？

不是。它只是结构化输入与输出的前端演示，不执行代码分析、现有技术检索或法律判断。完整分析由安装后的 skill 在用户指定材料范围内完成。

支持哪些输入材料？

skill 可处理用户提供的设计文档、研发报告、源代码、接口说明和测试材料。演示页只接受粘贴的文本摘录；本地文件解析能力取决于运行 skill 的助手环境。

候选专利点是否代表可以申请或授权？

不代表。候选点是依据技术材料整理的讨论假设。发明人需核对事实、贡献与公开时间，并由专利专业人士评估现有技术、保护范围和申请策略。
